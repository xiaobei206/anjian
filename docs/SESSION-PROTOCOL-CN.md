# GPT 网页会话协议与交接流程

本文件解决一个问题：不同 GPT 会话有独立上下文和长度限制，项目必须依靠 Git 中的状态文件连续推进。

## 1. 单一事实来源

- 仓库 main 是项目事实来源。
- README 是导航。
- AGENTS 是跨会话协作规则。
- SESSION-HANDOFF 是当前状态和唯一下一任务。
- ROADMAP 是全部工作清单。
- PRD / ARCHITECTURE / API / RECORDER / ACCEPTANCE 是需求和技术规范。
- DEVELOPMENT-LOG 是历史记录，不代替当前 handoff。
- DECISIONS 是已定和待验证决策。

聊天记录可作为补充背景，但不得覆盖 Git 文档。

## 2. 每个会话的标准流程

### 开始
1. 读取 AGENTS、README、SESSION-HANDOFF、ROADMAP。
2. 检查最新 main HEAD 和仓库内容。
3. 读取当前任务相关设计文档。
4. 用自己的话确认：目标、范围、交付文件、验收条件。
5. 不重复询问仓库里已明确的内容；只有遇到真正阻塞且无法合理作出保守选择时才向用户询问。

### 执行
1. 只做 handoff 指定任务。
2. 先检查现有实现，防止重复开发。
3. 复杂任务拆为可验证的小步骤。
4. 在任务关键检查点及时提交，不要把所有修改堆到会话最后。
5. 所有失败、暂时无法验证和外部限制都如实记录。

### 收尾
1. 运行任务要求的构建、测试或检查。
2. 检查 Git diff，排除无关修改、密钥和生成物。
3. 更新 DEVELOPMENT-LOG。
4. 更新 ROADMAP 状态。
5. 重写 SESSION-HANDOFF，指定下一会话唯一任务。
6. 有决策变化时更新 DECISIONS 和相关规格。
7. 提交 main，确认最新 commit SHA。
8. 最终告诉用户实际完成了什么、验证了什么、commit SHA 和下一任务。

## 3. Token / 上下文预算使用方式

用户希望每个网页会话尽可能完成更多有价值的工作。执行规则：
- 将上下文主要用于当前任务的设计、实施、测试和修复，而不是重复解释项目背景。
- 不要为了“用尽 Token”添加无关功能、反复大段重述文档或在最后一刻启动无法验收的大任务。
- 为避免被突然截断，优先在预计上下文不足前留出收尾空间，提交一个可继续的检查点。
- 如果任务较大，可以先完成一个完整子目标再决定是否继续；必须确保即使本轮立即结束，仓库状态仍能被下一会话接手。
- 不以“剩余 Token 很少”作为交接策略；以可验证检查点为准。

## 4. 会话编号与 handoff

使用 S000、S001、S002……顺序编号。
每个 handoff 至少包括：
- 当前项目阶段 / 版本状态
- 当前 main commit SHA
- 本会话上一个已完成任务
- 当前实现/文档事实
- 未解决问题和阻塞
- 下一会话唯一任务 ID
- 下一任务目标、范围内/范围外
- 交付文件
- 验收命令/步骤
- 完成后必须更新哪些文件

## 5. 遇到意外截断

如果上个会话没有正常结束：
1. 以最新 main commit 为准，不假设聊天里的最后计划已执行。
2. 检查 SESSION-HANDOFF 和 DEVELOPMENT-LOG。
3. 如果存在未提交内容或外部工作区状态不可确认，先检查再处理；不可盲目覆盖。
4. 没有新的 handoff commit 时，按最近一次有效 handoff 的“未完成任务”继续。
5. 如果代码已提交但 handoff 未更新，先基于 Git 历史补齐交接文件再继续。

## 6. 最终回复模板

- 本轮任务：
- 实际完成：
- 变更文件：
- 验证结果（PASS/FAIL/BLOCKED/NOT RUN）：
- commit SHA：
- 当前阶段：
- 下一会话任务：
- 新会话提示词：

不要把未完成工作描述为已完成，不要仅以“已更新 Git”作为交付说明。
